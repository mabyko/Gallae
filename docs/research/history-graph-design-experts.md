# History 그래프: 공개된 UX·시각화 전문가 조언

조사일: 2026-10-02. 공개된 저자 본인의 글을 확인했다. 인터뷰나 Gallae에 대한 직접 자문이 아니며, 아래 적용안은 조사자의 해석이다. 앱 코드와 시안은 변경하지 않았다.

## 현재 시안 진단 — 코드와 화면을 보고 내린 판단

혼합안은 약 2.1px 선의 색을 배경색에 섞는 변화가 중심이다. 노드 크기와 넓은 브랜치 배지·커밋 텍스트는 거의 같아, 화면 전체에서 변한 면적이 작다. 이미 있던 HEAD 링을 다시 사용하는 것만으로는 경로 전체의 구별이 크게 달라지지 않는다. 사용자의 “티가 잘 안 난다”는 피드백을 반영해, 다음 비교에서는 색 농도 외에 형태나 강조 면적을 실제로 바꿔야 한다. 이는 Gallae 시안에 대한 판단이며 외부 사용성 실험의 결론이 아니다.

Kelley Gordon의 NN/g 글 [Visual Hierarchy in UX](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/)도 색·대비뿐 아니라 크기와 묶음을 함께 다룬다. 멀리서 보거나 눈을 가늘게 뜨고 보는 방식으로 어떤 요소가 먼저 두드러지는지 확인하라고 제안한다. Gallae에서는 작은 미리보기를 확대해야 차이를 느끼는지, 원래 작업 크기에서도 경로가 보이는지를 확인하는 데 응용할 수 있다.

## 다른 제품의 공개된 처리 방식

다음은 공식 자료에서 확인한 동작이다. 실제 설치판을 조작하거나 경쟁 제품의 코드를 복사한 것이 아니다.

| 제품·공식 출처 | 확인한 방식 | Gallae에 적용할 때의 해석 |
|---|---|---|
| [IntelliJ IDEA — Log](https://www.jetbrains.com/help/idea/log-tab.html) | 보기 설정 안에서 내 커밋은 굵게, 병합 커밋은 회색으로, 현재 브랜치는 파란 배경으로 강조한다. | 색 농도 하나가 아니라 서로 다른 시각 속성으로 의미를 구분한다. Gallae는 현재 브랜치 소속 표시와 클릭한 행 표시가 겹치지 않게 해야 한다. |
| [JetBrains — Table 디자인 가이드](https://plugins.jetbrains.com/docs/intellij/table.html) | 데이터 집합을 구분할 때 배경 띠를 쓸 수 있으며 현재 브랜치 예시를 제공한다. 동질적인 데이터에 불필요한 교대 배경은 두 겹의 시선 중심을 만든다고 설명한다. 선택된 행은 별도의 시스템 선택 상태를 따른다. | 모든 행에 줄무늬를 추가하기보다, 의미가 있는 HEAD 소속 구간에만 짧은 표시를 시험한다. |
| [Fork — Release Notes](https://git-fork.com/releasenotes), 2.53, 2025-05-21 | 브랜치 라벨을 대응하는 그래프 색으로 그리는 개선을 기록했다. | 경로와 브랜치 이름을 같은 색으로 연결하면 선의 출발점을 찾기 쉬워질 수 있다. |
| [GitLens — Commit Graph](https://help.gitkraken.com/gitlens/gl-commit-graph/) | Smart Branches는 현재 브랜치, upstream, base/target 브랜치를 보여 주는 방법을 제공한다. | 더 강한 집중이 필요하면 별도 보기 범위를 제공할 수 있다. 이는 왼쪽 배치 기준과 다른 기능이다. |

## 다음 시안 제안 — 근거를 응용한 가설

가장 먼저 비교할 안은 **경로를 따라가는 지도 표식**이다. 이미 있던 HEAD 링만 유지하는 데 그치지 않고 현재 작업 경로의 일반 노드를 더 크게 만들며, `HEAD` 배지와 경로 색을 일치시킨다. HEAD 경로는 선명한 중심선과 얇고 선명한 외곽선으로 다른 선과 분리한다. 흐린 후광을 더 강하게 만드는 대신 모양 자체가 다른 표시를 시험한다. 다른 가지는 기존 색을 유지한 채 한 단계 부드럽게 한다. 이 구체적인 이중선 처리 자체가 전문가의 직접 권고인 것은 아니다.

두 번째 비교안은 **현재 작업 커밋의 행 앞부분을 표시**하는 것이다. 기존 C안의 노드 주변 작은 띠에서 나아가, 그래프와 브랜치 배지 영역에 걸친 짧은 배경 면으로 강조 면적을 키운다. 현재 작업 커밋인 행에만 표시하고 중간에 끼어든 다른 브랜치의 행은 칠하지 않는다. 클릭한 커밋은 기존의 행 전체 선택 배경을 사용해 두 의미를 구분한다. 배경이 가지 색을 왜곡하거나 선택 상태와 혼동되는지는 검증해야 한다.

색을 보존하는 것과 중요도가 한눈에 보이는 것은 별개다. 숫자 하나로 opacity를 정답처럼 정하지 말고, 밝은 화면·어두운 화면·좁은 폭·여러 가지가 교차하는 이력에서 비교한다. 커밋 제목과 브랜치 라벨은 읽을 수 있는 상태를 유지한다.

도구 모음에는 **보기 설정 진입점 하나**를 두고, 그 안에 `왼쪽 기준: 기본 브랜치 / 현재 HEAD`를 배치한다. 넓은 화면에서는 짧은 `보기` 라벨, 좁은 화면에서는 같은 위치의 아이콘과 툴팁/접근성 이름을 쓰는 시안을 비교할 수 있다. 현재 배치 기준은 기존 History 보조 문구에 표시하면 별도 넓은 컨트롤 없이도 상태를 알 수 있다. 메뉴를 닫은 뒤 상태가 전혀 안 보이는 방식은 피한다.

## 의미를 분리할 것

- **HEAD**: 현재 워크트리의 체크아웃 위치. 링·직접 라벨·경로 형태로 표현한다.
- **배치 기준**: 어느 브랜치를 왼쪽에 놓는지. 위치와 보기 메뉴의 체크 상태로 표현한다.
- **선택한 커밋**: 사용자가 클릭해 상세 내용을 보는 대상. 기존 행 선택 배경으로 표현한다.

공통 조상에서 강조를 끝내는 것은 '현재 브랜치만의 작업'을 보여 주는 모드일 때 적합하다. 단순히 'HEAD의 조상 경로'를 보여 주는 것이라면 이어지는 경로도 맞다. 어떤 의미인지 정하지 않은 채 시각 효과만 바꾸면 사용자가 강조 범위를 오해할 수 있다. 이 구분은 Git 그래프에 적용한 설계 제안이며 위 전문가들이 제시한 Git 규칙은 아니다.

## 최소 비교 방법

동일한 이력에 현재안·지도 표식안·행 앞부분 강조안을 나란히 놓고 다음을 확인한다. 아래 시간은 연구 결과가 아니라 짧은 비교를 위한 임시 기준이다.

1. 2초만 보고 현재 HEAD가 어디인지 찾을 수 있는가?
2. HEAD부터 분기점까지 다른 가지로 잘못 넘어가지 않고 따라갈 수 있는가?
3. 다른 커밋 행을 선택해도 HEAD와 선택한 커밋을 구별하는가?
4. 좁은 창에서 배치 기준을 확인하고 변경할 수 있는가?

선호도만 묻기보다 찾는 시간과 잘못 짚은 가지를 함께 본다. 공개 자료는 이런 방향을 뒷받침하지만 Gallae에서 어떤 안이 가장 낫다는 실험 결과를 제공하지는 않는다.
